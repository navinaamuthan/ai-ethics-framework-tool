# One-month AIEF fix cycle + dissertation re-evaluation

This plan does three things in sequence: (1) wire the mitigation taxonomy into
the live pipeline instead of leaving it as free LLM text, (2) add the
consistency-checking SHACL layer Dave described, alongside the existing
feature-to-risk shapes, not replacing them, and (3) re-run the diagnostic
pipeline (Steps 1-6 under `diagnostic/`) on the changed SHACL/RAG outputs and
update the dissertation with the new numbers. AIEF changes are not time-boxed
tightly; the dissertation's diagnostic methodology chapters do not change in
substance; only the Implementation/Evaluation numbers that depend on AIEF's
outputs get regenerated.

Do not skip the verification step at the end of each week. Each week's fix
must be confirmed working on a small sample before moving to the next week.

---

## Week 1 — Wire the mitigation taxonomy into retrieval and the prompt

### Current state (verified)

`ontology/ai-ethics-final.ttl` already defines:
- `:Mitigation` (class), with two subclasses `:TechnicalMeasure` and
  `:OrganisationalMeasure`
- Five `:TechnicalMeasure` instances: `:Encryption`, `:Pseudonymisation`,
  `:Anonymisation`, `:AccessControl`, `:AuditLog`
- Seven `:OrganisationalMeasure` instances: `:StaffTraining`,
  `:GovernanceProcedure`, `:ComplaintMechanism`, `:IncidentResponsePlan`,
  `:EthicsReviewBoard`, `:HumanOversight`, `:ResponsibleReleasePolicy`
- An object property `:hasMitigation` (domain: requirement, range:
  `:Mitigation`)
- Exactly one usage: `:R071 :hasMitigation :Encryption, :AccessControl`

`rag-pipeline/sparql_retrieval.py` and `rag-pipeline/prompt_builder.py` never
query `:hasMitigation` or `:Mitigation`. The `recommended_mitigations` field in
every AIEF output is unconstrained free text generated by the LLM per
proposal, with no connection to this taxonomy.

### Task 1.1 — Populate `:hasMitigation` across the 207 requirements

Write `ontology/populate_mitigations.py`. For each of the 207 requirements,
assign one or more `:hasMitigation` values from the 12 existing mitigation
classes, using the requirement's existing `:hasRisk` categories as the basis
for assignment (do not invent a new taxonomy; map to what already exists).
Use a rule table, not free-form LLM generation, so every mapping is
auditable:

| Risk category (from `:hasRisk`) | Suggested mitigation(s) |
|---|---|
| PrivacyBreach, DataBreach, Surveillance | `:Encryption`, `:Pseudonymisation`, `:AccessControl` |
| DataGovernance | `:AuditLog`, `:GovernanceProcedure` |
| Discrimination, biased outcomes | `:StaffTraining`, `:EthicsReviewBoard` |
| PhysicalHarm, safety-critical | `:HumanOversight`, `:IncidentResponsePlan` |
| Reputational/legal risk, dual-use | `:ResponsibleReleasePolicy`, `:GovernanceProcedure` |
| Complaint/appeal-related (liberty, effective remedy) | `:ComplaintMechanism`, `:HumanOversight` |
| Anything not covered by the above | leave unmapped — do not force a mitigation onto a requirement where none of the 12 classes fit; report the unmapped count honestly rather than padding coverage |

This is a deliberately simple, auditable rule table, not a new ML
classifier. Write it as an explicit Python dict from risk-category string to
list of mitigation IRIs, apply it, and emit the resulting `:hasMitigation`
triples as a TTL fragment (`ontology/mitigation_population.ttl`), then merge
into `ai-ethics-final.ttl`. Print a coverage report: how many of 207
requirements now have at least one `:hasMitigation`, and how many remain
unmapped. **Report this number honestly in the dissertation update — do not
claim 100% coverage if it isn't.**

### Task 1.2 — Wire `:hasMitigation` into retrieval

In `rag-pipeline/sparql_retrieval.py`, extend whatever function currently
retrieves matched Charter rights/risk categories for a proposal to also
retrieve the `:hasMitigation` values attached to the retrieved requirements.
Add this to the retrieval context object returned to `prompt_builder.py`
(e.g. `retrieved_mitigations: list[str]`, deduplicated).

### Task 1.3 — Change the prompt to constrain mitigations, not free-generate them

In `rag-pipeline/prompt_builder.py`, `build_assessment_prompt()`: add a new
context block listing the retrieved mitigation options (from Task 1.2),
alongside the existing requirements/rights/incidents context. Change the
instruction text for `recommended_mitigations` from open free-text generation
to: *"For each mitigation, select from the retrieved mitigation options where
applicable; if none of the retrieved options adequately address the risk,
you may propose a specific alternative, but state explicitly that it is not
drawn from the modelled taxonomy."* This keeps the system honest: most
mitigations should now trace to the ontology, but the LLM is not forbidden
from proposing something outside it when genuinely needed. Track, in the
output JSON, a boolean `from_taxonomy: true/false` per mitigation so this is
measurable later.

### Task 1.4 — Verify

Run the pipeline on 5 proposals spanning risk levels. Confirm:
- retrieved mitigation options actually appear in the prompt context
- the `recommended_mitigations` output now cites taxonomy mitigations more
  often than not (report the actual fraction, don't assume 100%)
- `from_taxonomy` flag populates correctly

## Week 2 — Add the consistency-checking SHACL layer (Dave's suggested design)

### Current state (verified)

All 21 shapes in `shacl/aief-risk-shapes.ttl` target `aief:ResearchProposal`
and fire on stated proposal features to derive a risk (e.g.
`BiometricConsentShape` fires when biometric data lacks opt-in consent).
None of them take an already-produced assessment (a stated risk + its cited
requirements + its recommended mitigations) and check those three things are
mutually consistent. That is Dave's suggested design, and it does not
currently exist.

### Task 2.1 — Design the new shape file, additive not replacing

Create `shacl/aief-consistency-shapes.ttl`, a second, independent shape file.
Do not modify `aief-risk-shapes.ttl` — the feature-to-risk shapes remain as
they are; this is a new validation pass over an LLM or SHACL assessment
*output*, not over the raw proposal.

This requires the LLM's JSON output (or the SHACL feature-derived risks) to
first be lifted into RDF triples so SHACL can validate them. Write
`rag-pipeline/output_to_rdf.py`: takes an assessment JSON object (the same
shape produced by `build_assessment_prompt`'s schema) and emits an RDF graph
with a node per `identified_risk`, linked via new properties
`:assessmentCitesRequirement`, `:assessmentHasMitigation`,
`:assessmentRiskCategory`.

### Task 2.2 — Write the consistency shapes

At minimum, three consistency shapes, each targeting the per-risk node
produced by Task 2.1:

- `RiskHasRequirementShape`: every `identified_risk` node must have at least
  one `:assessmentCitesRequirement`. Violation message: "A risk was
  identified with no supporting requirement citation."
- `RiskHasMitigationShape`: every `identified_risk` node must have at least
  one `:assessmentHasMitigation`. Violation message: "A risk was identified
  with no corresponding mitigation."
- `MitigationCategoryMatchShape` (the substantive one): the mitigation(s)
  attached to a risk must belong to a `:Mitigation` subclass whose typical
  use (per the Week 1 rule table) matches the risk's category — e.g. a
  `PrivacyBreach` risk mitigated only by `:StaffTraining` (an organisational
  measure with no technical bearing on data handling) should fail this
  shape. Implement via `sh:sparql` constraints referencing the same
  risk-category-to-mitigation-class table from Task 1.1, so the two are
  never allowed to drift apart.

### Task 2.3 — Wire into evaluation, not just standalone validation

Add a `run_consistency_check.py` script under `shacl/` that runs these three
shapes over every proposal's assessment output (all four AIEF configurations)
and reports, per configuration: fraction of risks with a supporting
requirement citation, fraction with a mitigation, fraction whose mitigation
category matches. This becomes a new, small property table for the
dissertation, not a redesign of the Stage-2 property suite already reported
(stability/traceability/amendability/comprehensibility stay as they are;
this is additional evidence, presented as such).

### Task 2.4 — Verify

Run on 5-10 proposals. Confirm violations are being caught (deliberately
construct one broken test case with a mismatched mitigation to confirm the
shape actually fires) before running at scale.

## Week 3 — Re-run the diagnostic pipeline on the changed AIEF outputs

Because Weeks 1-2 change what SHACL and the RAG pipeline produce, the four
assessor configurations now behave differently, and every diagnostic number
in `Evaluation.tex` that depends on assessor outputs needs regenerating. The
diagnostic methodology itself (Design.tex) does not change.

### Task 3.1 — Re-run assessor outputs

Re-run all 40 proposals through all four configurations (SHACL, LLM-8B,
LLM-70B, keyword-baseline) with the Week 1-2 changes live. Keep the old
outputs archived (`evaluation/results/pre-mitigation-fix/`) rather than
overwritten, so before/after can be reported if useful.

### Task 3.2 — Re-run `diagnostic/` Steps 3-6

The corpus (Step 1) and frame annotations (Step 2) do not need to change —
those are about label reliability, not assessor behaviour. Re-run:
- `reliability_analysis.py` (Step 3): assessor-vs-GT κ values will shift
  since SHACL's outputs changed; recompute the decision-rule table
- `perturbation_generator.py` (Step 4): re-run assessors on the 45 variants
- `property_evaluator.py` (Step 5): traceability and amendability almost
  certainly change now that mitigations are taxonomy-linked and consistency
  is checked; re-run the degenerate-baseline control specifically, since
  that was the one that failed before — report honestly whether it still
  fails or not
- `generate_tables.py` (Step 6): regenerate all `.tex` tables

### Task 3.3 — Verify against the same checks as before

Same discipline as the original run: leave-one-out stability, bootstrap CIs,
the three pre-registered kill conditions. Do not cherry-pick a favourable
re-run; report the new numbers exactly as they come out, confirmatory or not.
